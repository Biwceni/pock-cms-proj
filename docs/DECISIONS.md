# Decisões da POC

- Framework: Next.js 16.4.0 com App Router.
- CMS: Payload 3.90.2 com `@payloadcms/db-postgres` 3.90.2, usando Supabase Postgres pelo Session pooler e o schema `payload`.
- Editor visual: pacote `@puckeditor/core` 0.23.0 e CSS `@puckeditor/core/puck.css`.
- Banco: manter as tabelas preexistentes do schema `public`; o Payload passa a usar o schema `payload`. Nenhuma tabela antiga foi removida ou movida.
- Admin: usar o admin nativo do Payload; o painel customizado anterior fica preservado em `_legacy/`, excluído do roteamento e do TypeScript build.
- Primeiro usuário: a operação nativa `registerFirstUser` cria o usuário com `overrideAccess: true`; o hook `beforeChange` confirma que `users` está vazia e força `role: admin` somente nesse primeiro cadastro. Os seguintes mantêm `editor` como padrão.
- Acesso a páginas: visitantes leem somente publicadas; `editor` pode criar/editar e excluir somente rascunhos; `admin` pode gerenciar todas as páginas e usuários.
- Rascunhos: usar o recurso nativo de versions/drafts do Payload, que expõe `_status`.
- Interface do admin: tradução portuguesa `pt` do Payload e rótulos de coleção/campo explícitos em pt-BR.
- O conteúdo frontend é renderizado a partir do campo `puckData`, com blocos em português e valores padrão prontos para uso.
- O fluxo de criação de página usa apenas o título e gera slug automaticamente antes do primeiro salvo.
- Testes de integração da matriz de acesso usam a Local API com `overrideAccess: false`, credenciais aleatórias e o schema isolado `payload_test`. Podem usar `PAYLOAD_TEST_DATABASE_URI`; se ausente, reutilizam `DATABASE_URI`, sempre limitados a esse schema. O contexto `disablePageRevalidation` evita chamar a revalidação do Next.js durante os testes.
- Fase 2: `puck/config.render.tsx` é uma configuração mínima e segura para Server Components com os blocos `Heading` e `Text`; o `Render` vem de `@puckeditor/core/rsc`. A rota pública usa ISR de 1 hora e invalidação de caminho pelos hooks do Payload.
- A configuração de renderização da Fase 2 é provisória; `src/puck/config.tsx` e `src/components/PuckEditorClient.tsx` serão revistos nas Fases 3 e 4. A tela de renderização permanece independente do editor.
- O seed `npm run seed:phase-2` exige `PAYLOAD_SEED_EMAIL` e `PAYLOAD_SEED_PASSWORD`, autentica um administrador existente e cria uma página publicada e outra em rascunho com slugs únicos; nunca inclui credenciais no código.
- `npm run verify:phase-2:production` parte de um build existente e sobe `next start` no schema isolado `payload_test`; cria credencial aleatória pelo endpoint nativo de primeiro usuário, verifica leitura/revalidação pela API REST e remove os dados de teste ao terminar. `PAYLOAD_TEST_DATABASE_URI` pode apontar para a conexão de teste; o script exige que `payload_test.users` e `payload_test.pages` estejam vazias e nunca usa `public`.
- Fase 3A: o editor visual é uma view server-side do admin nativo em `/admin/puck-editor/:collection/:id`, limitada a `pages`; exige sessão autenticada e executa a leitura e a verificação de update com o principal completo (`req.user`) e os access controls do Payload. A view entrega ao cliente apenas os dados já permitidos.
- Fase 3A: o editor tem somente `Heading` e `Text`. O salvamento é manual pela API REST nativa (`PATCH /api/pages/:id?draft=true` para rascunho e `draft=false` com `_status: published` para publicar); o cliente não grava cópias em disco nem em armazenamento local. A configuração `versions.drafts.autosave: false` mantém o autosave do Payload desabilitado; a confirmação de saída aparece enquanto houver alterações pendentes. A validação Zod, controles no campo e criação guiada de páginas ficam para a Parte 3B.
- Parte 3B: o campo `puckData` da coleção `pages` usa um componente customizado no admin nativo que mostra um resumo ("N blocos nesta página") e um botão "Abrir editor visual"; o JSON bruto fica oculto para o editor. A validação de servidor roda em `beforeValidate` e usa Zod para aceitar os tipos de bloco registrados na configuração, além de impedir payloads maiores que 250 KB, mais de 100 blocos e estruturas com profundidade superior a 8; todas as mensagens são em pt-BR.
- O fluxo guiado "Nova página" (informar somente o título e abrir o editor visual automaticamente) foi adiado para a Fase 5. Atualmente, cria-se a página pelo fluxo nativo de criação do Payload, informa-se o título e salva-se o rascunho; depois, em editar página, clica-se em "Abrir editor visual" no campo "Conteúdo da página".
- Fase 4 (Onda 1): os sete blocos (`Banner`, `CardGrid`, `Heading`, `Text`, `Image`, `Button`, `Spacer`) são registrados em `src/puck/blocks/registry.ts`, que é a fonte compartilhada para os tipos permitidos e schemas Zod. Há um arquivo de render por bloco; `src/puck/config.tsx` (editor) e `puck/config.render.tsx` (site/Server Components) reutilizam o mesmo renderizador. Categorias e campos usam rótulos pt-BR; `CardGrid.cards` é uma lista editável e as propriedades de mídia usam o `MediaPickerField`.
- Fase 4: `puck/tokens.css` fornece tokens visuais carregados pelo site e pelo admin. `MediaPickerField` lista a biblioteca REST nativa `/api/media`, normaliza as seleções no formato `{ id, url, alt, width, height }` e envia uploads multipart à mesma API, preservando os access controls da coleção `media`.
- Fase 4: validação server-side e render protegem URLs de links e imagens. Links aceitam somente caminhos relativos e `http(s)`, `mailto`, `tel`; imagens aceitam caminhos locais ou `http(s)`. Esquemas ativos como `javascript:` e `data:` são recusados, e o render não emite link/imagem quando recebe um valor inválido. Os componentes de imagem usam `next/image` com `unoptimized` porque os uploads podem ter origem/CDN variável, sem depender de allowlist de hosts. O limite estrutural foi ajustado para profundidade 8 para acomodar a hierarquia CardGrid > lista > card > mídia, mantendo teto finito.
- Mídia desnormalizada: o seletor grava no `puckData` a URL como caminho relativo ao site (por exemplo, `/api/media/file/nome-do-arquivo.jpg`), sem host. URLs absolutas do mesmo host são convertidas para caminho relativo antes de salvar. Pendência: se o arquivo for substituído ou apagado, o objeto desnormalizado pode manter uma URL antiga; avaliar resolver a mídia pelo `id` ou limpar/atualizar referências em uma etapa futura.
- Testes da Onda 1 em `npm run test:integration` usam `payload_test` para Local API, nunca `public`: verificam que editor e site registram a mesma função de render para cada um dos sete tipos, criação de um rascunho contendo todos os blocos e mídia aninhada em CardGrid, rejeição de JSON inválido, tipos desconhecidos, conteúdo acima de 250 KB, link `javascript:` e imagem `data:` tanto ao salvar rascunhos quanto ao publicar; além da matriz de acesso, leitura pública e slug único.
- Correção da view do Puck: a rota está registrada em `admin.components.views` e era reconhecida pelo Payload; o 404 autenticado vinha da própria view, que procurava `params.collection` e `params.id`. No catch-all `app/(payload)/admin/[[...segments]]`, Next 16 entrega `params.segments` (`['puck-editor', 'pages', ':id']`), sem esses campos nomeados. A view agora valida e extrai coleção e ID desses segmentos, mantendo a allowlist de `pages` e a verificação de acesso de atualização no documento. `npm run test:editor-route` verifica que o acesso anônimo recebe login sem o editor e que o usuário autenticado autorizado recebe o editor em HTTP 200; a suíte Local API também testa um usuário autenticado cujo acesso de update ao documento é negado. A rota rejeita coleções fora da allowlist. O teste HTTP requer servidor Payload ativo, `PUCK_EDITOR_TEST_PAGE_ID` e credenciais por variáveis de ambiente (`PUCK_EDITOR_TEST_EMAIL`/`PUCK_EDITOR_TEST_PASSWORD` ou os pares separados `PUCK_EDITOR_TEST_EDITOR_EMAIL`/`PUCK_EDITOR_TEST_EDITOR_PASSWORD` e `PUCK_EDITOR_TEST_ADMIN_EMAIL`/`PUCK_EDITOR_TEST_ADMIN_PASSWORD`), para evitar credenciais fixas.
- Avaliação (não adotado): `@delmaredigital/payload-puck` foi conferido na versão publicada `0.9.5`; os peer dependencies declaram Payload e `@payloadcms/next` `>=3.69.0`, portanto incluem `3.90.2`, e a licença publicada é MIT. O repositório recebeu atualização em conjunto com essa versão e o README informa uma correção de segurança na `0.9.3`. A POC mantém o editor próprio para preservar o fluxo de autorização, drafts e validação controlados pelo projeto; nenhuma dependência do plugin foi instalada.
- Fase 5A: o `access.admin` da coleção `users` permite que usuários autenticados abram o admin; leitura/criação/alteração/exclusão de usuários continuam restritas a administradores. Para editores, a coleção de usuários fica oculta por `admin.hidden` (que também exclui suas rotas do admin), e a leitura de versões continua protegida pelos access controls. O editor vê Páginas e Mídias. O atalho de API aparece somente para administradores; as URLs de API continuam servindo as operações autorizadas do editor, necessárias para salvar páginas e enviar mídias. O Payload mantém a confirmação nativa ao excluir; a regra de acesso impede editores de excluir páginas publicadas.
- Fase 5A: o SEO inicia recolhido, textos do admin e do Puck foram ajustados para pt-BR, e toda ação de publicar no editor visual pede confirmação. Após publicar, o editor mostra um link para abrir a página no site. A navegação de retorno aponta para a lista de Páginas.
- Fase 5B: a criação guiada usa uma view própria `/admin/nova-pagina`; o título é o único dado obrigatório, “Em branco” é o modelo padrão e “Serviços” é opcional. A view cria um rascunho pela API autenticada do Payload e abre `/admin/puck-editor/pages/:id`; o slug continua sendo gerado pelo hook da coleção.
- Fase 5B/atualização pré-Fase 7: o Payload mantém `versions.drafts.autosave: false`; o Puck, em view separada do formulário nativo, salva rascunhos via REST após 3 segundos sem alterações. Publicar continua manual e exige confirmação; saves são serializados e mudanças mais recentes enfileiradas.
- Histórico de versões: `pages.versions.maxPerDoc` agora é 20. Em `payload_test`, os primeiros cinco salvamentos criaram cinco linhas em `_pages_v`; depois de 21 saves, a tabela reteve 20 linhas no total, crescimento líquido de 19 sobre a contagem inicial. O Payload pode limpar versões antigas em lotes; versões antigas, inclusive publicações, podem ser descartadas ao atingir o teto.
- Debounce: o intervalo subiu de 1 s para 3 s para evitar criar versões a cada pausa curta de digitação e reduzir gravações. Isso reduz a frequência de persistência durante edição contínua, com risco de até 3 s de alterações ainda não enviadas; o indicador “Salvando em instantes…” e o aviso ao sair com mudanças pendentes permanecem. O salvamento manual continua disponível.
- Fase 7: `docs/USABILITY.md` contém o roteiro e modelo para teste moderado, ainda não executado. A cópia da especificação mencionada e sua seção 1.2 não estão no workspace; as tarefas foram elaboradas a partir do fluxo funcional atual e precisam ser comparadas com a especificação antes da sessão.
- UX do editor visual (Puck 0.23.0 instalado): os tipos publicados em `node_modules/@puckeditor/core/dist/index.d.ts` oferecem `overrides.header` (`actions`, `children`), `overrides.headerActions` (`children`), `ui`, `viewports` e `dictionary`. A mesma declaração marca `renderHeader`/`renderHeaderActions` como compatibilidade antiga; o runtime emite aviso e recomenda `overrides.header`/`overrides.headerActions` com `usePuck()`. `usePuck()` expõe `history.back()`, `history.forward()`, `hasPast` e `hasFuture`; os rótulos dos viewports são configuráveis e aparecem nos títulos de tooltip. A integração usará esses pontos atuais, sem `renderHeader`; o cabeçalho customizado omite as ações padrão do Puck para evitar botão Publicar duplicado. O editor ficará em view de tela inteira escondendo apenas o chrome do template Payload durante essa rota.
- Endereço e editor Puck: a view “Nova página” continua pedindo apenas título/modelo; no admin nativo, `Endereço` fica oculto na criação e para editores, e aparece a administradores somente após o documento existir. O hook existente segue responsável pelo slug único e por preservar slug de páginas publicadas. No Puck, o título da página é mostrado no cabeçalho e no campo somente leitura “Título da página”; não cria um segundo título editável desvinculado do documento. A barra do Payload fica oculta apenas enquanto a view do editor está montada; a barra única substituta usa `overrides.header`, rótulos de viewport e as ações manuais do editor.
- Fase 6: cookies do Payload usam `Secure` em produção e `SameSite=Strict`; login bloqueia após cinco tentativas por dez minutos. Uploads aceitam somente JPEG, PNG, WebP, GIF e AVIF, com limite de 5 MiB por arquivo e 6 MiB por requisição multipart. CORS e CSRF não confiam em origens externas.
- Fase 6: `PAYLOAD_SECRET` não tem fallback fixo e precisa ser aleatório, com pelo menos 32 caracteres e diversidade mínima; a verificação em memória do ambiente local não passou. Atualizar o segredo manualmente; `.env` não foi exibido nem alterado.
- Fase 6: removidos do código atual o fallback fixo de conexão PostgreSQL e a senha fixa do bootstrap arquivado. `_legacy/` permanece, mas o bootstrap legado só pode prosseguir com `LEGACY_ADMIN_PASSWORD` configurada explicitamente. A varredura encontrou candidatos históricos em commits antigos; rotacionar as credenciais afetadas. Nenhum histórico Git foi reescrito.
- Fase 6: o E2E do fluxo público usa Chromium headless e `payload_test`; não depende de credenciais fixas. A revisão de dependências permanece com advisories sem correção compatível, descritos em `SECURITY.md`.
- Fase 6 — diagnóstico Git/npm: no histórico local, dois candidatos agrupados (URI PostgreSQL e senha literal de bootstrap) foram localizados em commits/linhas documentados em `SECURITY.md`. Ambos foram removidos do código atual, mas a validade externa não pode ser confirmada; rotacionar se já foram usados. Não há remoto/upstream/ref remota configurado, `.env` nunca foi versionado, e o histórico não foi reescrito.
- Fase 6 — dependências: overrides semver compatíveis atualizaram `undici` para `7.30.0` e `dompurify` para `3.4.16`; auditoria caiu de 21 para 14 alertas no grafo completo e de 17 para 10 em produção. Após a atualização, lint, build e 14 testes de integração em `payload_test` passaram. Restam 5 alertas altos em produção na cadeia Sass/Chokidar/Braces; não alterar essas dependências sem aprovação, pois o override pode mudar compilação CSS/observação de arquivos.
- Fase 6 — risco aceito: manter `sass@1.77.4` / `chokidar@3.6.0` / `braces@3.0.3` na POC, por serem dependências de build/desenvolvimento sem exposição direta a visitantes. Reavaliar antes do deploy na Vercel ou ao atualizar Payload. A release mais nova disponível na major 3 continua `3.90.2` e ainda declara Sass `1.77.4`; nada foi atualizado.
- Fase 6 — segredo: o valor local falha as regras de mínimo de 32 caracteres e de 16 caracteres distintos, mas não é um placeholder conhecido. O responsável vai gerar e configurar um valor novo; nenhum segredo foi exibido ou alterado.
- Fase 6 — histórico: o responsável deve rotacionar a senha do banco Supabase associada à URI candidata e qualquer credencial de bootstrap que tenha sido usada. Não reescrever Git; reavaliar apenas se o repositório for enviado a um remoto.
- E-mail: sem adaptador, o Payload registra mensagens de recuperação no console, mas não as entrega à caixa postal. A tela de login é anterior à autenticação e não consegue ocultar “Esqueceu a senha?” apenas para editores sem customização que revele se um e-mail corresponde a usuário/perfil. Recomendação pendente: configurar transporte SMTP local de desenvolvimento (por exemplo, Mailpit) e manter um adaptador de produção separado; não foi instalado nem configurado adaptador nesta etapa.
